O que é cada coisa, em uma frase

Antes do glossário — a distinção que resolve a maior confusão.

GRID é infraestrutura: as três máquinas da rede, descobertas, medidas e acessíveis por SSH com uma conta restrita. Não decide nada, não roteia missão nenhuma — só existe e responde quando chamado.

MRW é um motor de execução e roteamento que decide o quê rodar, onde, e com qual modelo — e que, desde a NEXT-006, sabe usar o Grid como um dos lugares onde pode executar. O MRW é o primeiro cliente do Grid, não o dono dele.

Glossário

Termos e siglas usados nos itens DOT/NEXT deste projeto, na ordem em que fazem mais sentido juntos.

GridMEIZEX Grid
As três máquinas da rede doméstica (Lenovo, Dell-A, Dell-B) disponibilizadas como recursos de execução: identidade de rede confirmada, capacidade real medida, código sincronizado, acesso remoto via SSH restrito. Vive em MEIZEX_GRID/.
MRWMEIZEX Router Worker
O motor de roteamento e execução do ecossistema. Decide qual recurso (modelo, ferramenta, ou — agora — nó do Grid) atende cada missão, e executa. Vive em MEIZEX_ROUTER_WORKER/, fora do subconjunto público do Grid (mas com uma cópia parcial lá, para os testes reais).
AIRMEIZEX_AIR
Sensor de capacidade de máquina: RAM efetiva (não só nominal), pressão de CPU/processos, executores encontrados (Python, PowerShell, runtimes de inferência). O Grid usa o AIR para medir cada nó antes de confiar nele.
DOT / NEXT / LAB / ARC
Protocolo de autoridade do projeto. DOT.md = decisões aceitas (não editar sem supersessão). NEXT.md = trabalho autorizado e seu resultado. LAB.md = hipóteses sem autoridade ainda. ARC.md = decisões superadas, preservadas com o motivo.
ResourceExecutor
O contrato do MRW que qualquer executor implementa: execute(request) → ResourceExecutionResult. Transporte-agnóstico por design — não sabe nem precisa saber se roda local ou na rede.
ProcessExecutor
Implementação padrão do ResourceExecutor que roda um comando como processo filho local, com JSON por stdin/stdout, timeout e ambiente restrito por allowlist.
RemoteSSHExecutor
Especialização do ProcessExecutor que troca o comando local por um comando SSH — o mesmo contrato, rodando num nó do Grid. Ganhou despacho assíncrono, cancelamento e limite de concorrência por nó (NEXT-008 a 010).
ResourceDispatcher
Laço de execução síncrono do MRW: recebe um plano com vários passos, escolhe o executor certo para cada um (por resource_id, não só por tipo) e roda em sequência.
Capability Routercapabilities/router.py
Camada de classificação de missão: lê o texto de uma missão, decide quais capacidades ela precisa, e escolhe o melhor recurso do registro para cada uma — sem executar nada. É essa camada que aprendeu a escolher o Grid sozinha (NEXT-011).
location
Campo novo em cada recurso do registro do MRW: "local", "grid" ou "cloud". Antes só existia local/cloud — não havia onde um nó confiável da rede se encaixasse honestamente.
grid_allowed
Campo de perfil de execução (ExecutionProfile). False por padrão: o Grid nunca é escolhido sozinho, fica na decisão manual. True: o roteador pode escolher automaticamente. O botão configurável pedido nesta sessão.
execution_boundary: "PROCESS"
Marca que um passo precisa rodar fora do processo do MRW — seja como processo filho local, seja num nó remoto do Grid. É o que impede o roteador de tentar rodar algo "in-process" quando precisa da fronteira real.
meizexgrid
A conta de sistema criada em cada Dell para o piloto SSH — sem privilégio administrativo, autenticação só por chave pública. É quem realmente executa o comando remoto, nunca a sua conta pessoal.
PORT_REGISTRY
Registro canônico de portas do ecossistema (PORT_REGISTRY/localhost.md), consultado antes de abrir qualquer serviço novo — inclusive o SSH de cada nó do Grid.
RemoteJobHandle
O que execute_async() devolve na hora: um objeto com done(), poll(), wait(timeout) e cancel() para acompanhar um job rodando em segundo plano num nó do Grid.

Arquitetura: quem depende de quem

O Grid não sabe que o MRW existe. O MRW é que aprendeu a falar com o Grid.

O Grid ficaria de pé mesmo se o MRW nunca tivesse sido tocado — discovery.py e o piloto SSH não importam nem sabem o que é um ResourceExecutor. Foi o MRW que ganhou um cliente novo (RemoteSSHExecutor) que fala com essa infraestrutura pelo protocolo dela (SSH), do mesmo jeito que qualquer outro orquestrador poderia.

As quatro perguntas

Respostas diretas, com o porquê.

01

O Grid é autônomo ou recurso do MRW?

Autônomo

O Grid não importa nada do MRW e não conhece o contrato ResourceExecutor. Ele é: rede descoberta, capacidade medida, uma conta SSH restrita por máquina. Isso funciona sozinho, testável sozinho — e foi construído e provado antes do MRW entrar na história (NEXT-001 a 005 não mencionam o MRW nenhuma vez).

O que existe hoje é o inverso do que a pergunta sugere: o MRW é que virou dependente do Grid como um dos lugares onde pode executar, através de um cliente específico (RemoteSSHExecutor) que fala o protocolo do Grid (SSH). Se amanhã o MRW for descontinuado, o Grid continua de pé — só perde esse cliente.

02

O MRW poderia ser aberto no GitHub, ou tem particularidades só nossas?

Os dois — separáveis

O núcleo de engenharia é genuinamente genérico e bem desenhado: o padrão ResourceExecutor/ResourceDispatcher, o roteador orientado a evidência (DECLARED → OBSERVED → VALIDATED, nunca promovido sem prova registrada), a fronteira de processo com ambiente restrito por allowlist — nada disso é específico do MEIZEX. É o tipo de coisa que projetos de orquestração de agentes reinventam com frequência.

O acoplamento pessoal está em outro lugar: caminhos absolutos do seu usuário (C:\Users\MEIZEX-ADMIN\...) espalhados em código e configuração, o catálogo de modelos LM Studio específico da sua máquina, provedores como chassis.py feitos sob medida, e o processo Windows-first (CREATE_NO_WINDOW, ACLs do OpenSSH) que é uma escolha válida mas não universal.

Nada disso é impeditivo — é trabalho real de generalização (extrair config de caminhos hardcoded, documentar o formato do registro, decidir o que fica proprietário) antes de publicar, não uma reescrita.

03

Se o Grid puder ser independente, ele seria um CLI?

Sim, é a forma natural

Já tem quase todas as peças de um CLI espalhadas: discovery.py (descoberta), o AIR já expõe um CLI de verdade (meizex-air probe, ponto de entrada declarado em pyproject.toml), e o piloto SSH é hoje uma sequência de comandos PowerShell manuais que se repete de máquina em máquina — exatamente o tipo de coisa que vira subcomando.

Um meizex-grid CLI coerente teria a cara de: grid discover, grid probe <nó>, grid pilot enable <nó> (o que hoje fazemos manualmente — perfil, ACL, firewall), grid dispatch <nó> -- comando. Nada disso exige o MRW; é a própria fronteira que este manual descreve.

04

Um espaço A2A no Grid, como intercâmbio de orquestradores — viável? Projeto à parte?

Viável, mas como projeto à parte

Tecnicamente plausível: os nós do Grid já aceitam comando de qualquer chamador que tenha a chave certa — não há nada no transporte que amarre isso ao MRW especificamente. Formalizar isso com um protocolo real de troca entre agentes (A2A da Google é o padrão aberto mais conhecido nessa categoria) resolveria exatamente o problema que já apareceu nesta sessão: LAB-002, ainda em aberto, registra que a única forma de coordenação entre este agente e o Codex hoje é manual — copiar um arquivo de missão, colar, esperar, ler o resultado depois.

Mas não pertence dentro do MEIZEX_GRID. O Grid é deliberadamente só a camada de acesso — descoberta, capacidade, transporte. Um protocolo de troca entre orquestradores é uma camada acima disso, do mesmo jeito que o MRW é: mais um cliente consumindo o Grid, não uma peça do Grid. Colocar A2A dentro do Grid misturaria "como eu chego numa máquina" com "como dois agentes decidem o que fazer entre si" — dois problemas diferentes que já estão separados hoje por acidente e deveriam continuar separados por decisão.

Nota à parte, não é A2A: o Kestra 2.0 (motor de orquestração de workflows, anunciado durante esta sessão) não resolve o mesmo problema — é um motor centralizado de flows, não agentes negociando entre si. Duas coisas dele valem registro: (1) "flows chamáveis como ferramenta via MCP" é o mesmo padrão que o MEIZEXLF-MCP já oferece no ecossistema, não A2A; (2) o modelo de workers desacoplados puxando de uma fila (Redis/AMQP/Kafka/JDBC, só acesso de saída) é uma alternativa de arquitetura madura ao SSH direto que o Grid usa hoje — resolveria o limite de concorrência (NEXT-010) de outro jeito, sem porta de entrada nenhuma no nó. Não é uma decisão para agora, só uma opção que existe.
